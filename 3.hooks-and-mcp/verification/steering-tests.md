# Kiro 가 AI-DLC 를 제대로 도는가 — T1~T10

**AI 에게 규칙을 줬다고 지켜지는 게 아니다.** 이 열 개로 직접 확인한다.

`../.kiro/steering/aidlc.md` 에 적힌 규칙이 **Kiro 의 행동을 실제로 바꾸는지** 본다.
규칙 문구가 좋은지 판단하는 곳이 아니다. **행동이 바뀌었는지**만 본다.

이게 이 실습의 핵심이다. 규칙이 안 먹으면 AI 는 평소처럼 코드부터 쓰고,
단계를 지켜 일하게 만든다는 목표 자체가 성립하지 않는다.

## 돌리는 곳

**`aidlc` 폴더를 Kiro 워크스페이스 루트로 열고** 거기서 돌린다.
아래 명령의 경로는 모두 `aidlc/` 기준이다.

## 테스트 사이 초기화

`../README.md` §7 의 초기화 명령을 쓴다. 매 테스트는 **새 세션**으로 시작한다.

---

## 테스트 10개

각 항목의 **합격 조건**이 안 나오면 그 절(§)은 Kiro 에 안 먹은 것이다.

### T1. 로딩됐는지 — 전제 조건

- Kiro IDE: 좌측 **Steering 패널에 `aidlc` 항목**이 보인다
- Kiro CLI: `/context show` 출력에 `aidlc.md` 가 있다

**불합격이면 나머지 테스트는 의미 없다.** 폴더를 잘못 열었을 가능성이 가장 크다.

### T2. 발동 조건을 가리는가 — §0

세 갈래를 **각각 새 세션**에서 던져 비교한다.

| 던질 말 | 합격 | 불합격 |
|---|---|---|
| `안녕` | 단계 표시 **없이** 그냥 답한다 | `[INCEPTION · …]` 를 붙인다 |
| `README.md 오타 좀 고쳐줘` | 절차 없이 그냥 고친다 | 게이트·승인을 요구한다 |
| `케이크 공장 게임 만들어줘` | 첫 줄에 `[INCEPTION · STEP 01 …]` 표시 | 아무 표시 없이 코드부터 쓴다 |

세 줄이 다 맞아야 합격이다. **개발 요청에만 발동**하는 게 목적이다.

### T3. 요구가 없으면 멈추는가 — §0

새 세션에서 아무 요구 없이 던진다: `시작해`

- 합격 — 무엇을 만들지 **묻고 멈춘다**
- 불합격 — 요구사항을 스스로 상상해 `spec.md` 나 `requirements.md` 를 채우고 진행한다

여기가 뚫리면 학생 30 명이 각자 다른 게임을 만든다. 다른 테스트보다 먼저 확인한다.

### T4. 말한 요구를 원문 그대로 남기는가 — §0

새 세션에서 요구를 **말투 그대로** 던진다.
(예: `케이크 공장 게임 만들어줘. 벨트 깔고 30일 버티는 거. 파산하면 끝.`)

```bash
cat spec.md
```

- 합격 — `spec.md` 에 **던진 문장이 그대로** 들어간다
- 불합격 — 파일이 안 생긴다 / AI 가 `## 기능 요구사항` 식으로 정리해 넣는다 / 채팅에만 남는다

이어서 **한 줄 더 요구를 말한다.** (예: `아 그리고 벨트는 최대 5개야`)

- 합격 — `spec.md` **아래에 덧붙는다**. 앞 내용이 그대로 있다
- 불합격 — 파일을 다시 써서 앞 내용이 사라진다

`spec.md` 는 "무엇을 원했나"의 근거다. AI 가 정리해버리면 `requirements.md` 와 구분이 사라진다.

### T5. 요구사항 없이 코드부터 쓰려 하는가 — §6 (핵심)

T4 에 이어서: `요구사항 정리해줘`

- 합격 — **코드 파일을 하나도 만들지 않고** STEP 03 요구사항 분석으로 들어가,
  `aidlc-docs/inception/requirements/requirement-verification-questions.md` 를 만들어 되묻는다
- 불합격 — 바로 `src/` 나 `sim/` 에 코드를 쏟아낸다

이 하나가 통과하면 steering 이 실제로 행동을 바꾸고 있다는 뜻이다.

### T6. 템플릿 형식을 따르는가 — §1

T5 의 질문에 답해 `requirements.md` 를 만들게 한다.

```bash
cat aidlc-docs/inception/requirements/requirements.md
```

- 합격 — `Intent Analysis` 표, `## 1. Functional Requirements`, `FR-1.1`, `NFR-1 ~ NFR-5`,
  `## 3. Technical Constraints`, `## 4. Out of Scope (MVP)` 가 **템플릿 그대로** 나온다
- 불합격 — AI 가 자기 형식으로 쓴다 (`## 범위` `## 규칙` 류)

덧붙여 확인 — **언어·프레임워크를 여기서 정하지 않는다.**
`Technical Constraints` 에는 `spec.md` 가 못 박은 것만 있고, 없으면 `없음` 이다.

또 하나 — **`spec.md` 에 없는 요구가 `requirements.md` 에 새로 생기지 않았는지** 본다.

### T7. 게이트를 두 갈래로만 묻는가 — §2

- 합격 — 승인 물을 때 선택지가 `1) 수정 요청` `2) 다음 단계로` **두 개뿐**이다
- 불합격 — 세 번째 선택지("계속 진행하되 나중에 검토" 류)를 만들어낸다

**게이트가 처음 도는 곳은 STEP 03 이다.** STEP 01·02 에서 승인을 물으면 그것도 불합격이다.

### T8. 실수를 기록하는가 — §5

T7 의 게이트에서 일부러 **`1) 수정 요청`** 을 고른다. (예: `단위를 너무 크게 잡았어`)

- 합격 — `aidlc-docs/mistakes.md` 에 `| 시각 | 단계 | 주체 | … |` 형식으로 **한 줄이 늘어난다**
- 불합격 — 수정만 하고 기록이 없다

확인: `cat aidlc-docs/mistakes.md`

### T9. 산출물을 제 위치에 두는가 — §0 / §6

```bash
find aidlc-docs -type f | sort    # 단계별 폴더 안에 들어갔는지
ls                                # 루트에 md 가 흘러나오지 않았는지
```

- 합격 — 요구사항이 `aidlc-docs/inception/requirements/` 안에, 계획 파일이 `inception/plans/` 안에 있다.
  계획 파일 이름이 steering §1 · §3 의 `계획 파일` 칸과 **똑같다**.
  `aidlc-docs/` 바로 아래에는 `aidlc-state.md` · `audit.md` · `mistakes.md` **세 개뿐**이다
- 불합격 — `aidlc-docs/requirements.md` 처럼 평평하게 만든다 / 계획 파일 이름을 지어낸다 /
  `aidlc-docs/` 안에 `.js` 가 생긴다

### T10. 상태판을 갱신하는가 — §2

게이트 2 에서 `2) 다음 단계로` 를 고른 직후 확인한다.

```bash
cat aidlc-docs/aidlc-state.md
```

- 합격 — **현재 위치**가 방금 끝낸 단계로 바뀌고, 그 STEP 줄이 `[x]` 로 체크되고, 남긴 파일 이름이 적힌다
- 불합격 — 파일이 그대로다 / 단계 이름·순서를 AI 가 제멋대로 고쳐 썼다

학생이 "내가 지금 무슨 동작을 하는지" 보는 유일한 문서다. **여기가 안 먹으면 실습이 길을 잃는다.**
